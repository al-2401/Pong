# CLAUDE.md

Вертикальный Pong на Flutter: ракетки на коротких сторонах экрана, мяч
отскакивает от них и от боковых стен. Сейчас есть игра против компьютера;
сетевая игра — следующий этап.

**Перед работой прочитай `docs/design.md`** — там зафиксированы все проектные
решения и их обоснования, включая уже принятые решения по сетевой игре
(раздел 9). Не переизобретай их. Если считаешь решение неверным — скажи и
объясни, но не меняй молча.

## Команды

```bash
flutter pub get
flutter analyze          # должен быть чистым
flutter test             # весь набор
flutter test test/engine # только физика и ИИ, headless, быстро
flutter run              # или flutter run -d <id>
```

Требуется Flutter >= 3.47 (`pubspec.yaml` просит Dart `^3.13.4`). Код
использует `Color.withValues`, поэтому ниже Flutter 3.27 не заработает при
любом констрейнте.

## Инварианты

Это не стилевые пожелания, а то, на чём держится архитектура.

1. **`lib/engine/` не импортирует Flutter.** Вообще. Именно поэтому физику
   можно тестировать без эмулятора и переиспользовать для сетевого матча без
   изменений. Если движку что-то понадобилось из Flutter — почти всегда это
   значит, что логика попала не в тот слой.
2. **Движок работает только в логических координатах:** `x` поперёк поля
   `0..1`, `y` вдоль поля `0..fieldLength`, единицы квадратные. Про пиксели,
   safe area и ориентацию экрана знает только
   `lib/ui/field_projection.dart`.
3. **`GameRules` против `Preferences`.** `GameRules` — всё, что влияет на
   симуляцию; должно быть одинаковым у обоих игроков и сериализуется в JSON
   для будущего рукопожатия хост↔гость. `Preferences` — локальные вкусы, на
   симуляцию не влияют. Не переносить одно в другое.
4. **Ракетки всегда на коротких сторонах экрана.** Отсюда следует, что
   ландшафт — это тот же матч, повёрнутый на 90° при отрисовке, а не вторая
   игра со своим балансом.
5. **Ввод только через `PaddleController`.** Палец, ИИ и (позже) соперник по
   сети — три реализации одного интерфейса. Движок не должен узнать, кто
   двигает верхнюю ракетку.
6. **Симуляция идёт фиксированным шагом** (`GameEngine.fixedStep`), отдельно
   от частоты кадров. Ничего, что зависит от `dt` кадра, в движке быть не
   должно.
7. **Столкновения только swept.** Проверка «мяч внутри ракетки» пропускает
   быстрый мяч сквозь ракетку. На это есть регрессионный тест.

## Структура

```
lib/engine/    симуляция, правила, ИИ — чистый Dart
lib/input/     управление пальцем
lib/ui/        отрисовка, проекция поля на экран, экраны
lib/settings/  локальные предпочтения
lib/stats/     рекорды
lib/audio/     звук
test/engine/   физика, ИИ, ход матча — headless
test/ui/       проекция поля, сквозной сценарий по экранам
```

## Договорённости

- Комментарии и имена в коде — на английском. Документация в `docs/` и
  `README.md` — на русском.
- Любое изменение в `lib/engine/` сопровождается тестом. Движок покрывается
  headless, это дёшево, пользуйся этим.
- Комментарий объясняет **почему**, а не что. «Так надо» и пересказ кода не
  нужны.
- Принял новое проектное решение или отменил старое — обнови
  `docs/design.md` в том же коммите.
- Новая зависимость — только с моего согласия. В проекте нет пакета
  управления состоянием и он не нужен: одна игровая сцена, `ChangeNotifier` и
  `InheritedWidget` хватает.
- Числа в `lib/engine/difficulty.dart` и модель в `paddle_motion.dart` —
  баланс, а не константы «как получилось». Менять их осознанно и говорить,
  что именно изменилось в ощущениях.

## Что не проверено

- Нативная сборка Android и iOS: проект создан в облачном окружении без
  Android SDK и Xcode, `flutter build` там не запускался.
- Задержка звука на устройстве (`audioplayers`, `PlayerMode.lowLatency`).
  Сервис уходит в тишину при любой ошибке плагина, так что молчание — это не
  обязательно отсутствие проблемы.
- Баланс сложностей: ладдер проверен только прогонами ИИ против ИИ.
